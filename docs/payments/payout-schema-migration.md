# Payout request consolidation

## Goal

Make payouts/{payoutId} the canonical record for both a participant cashout request and the
Xendit payout execution. The previous split was payoutRequests/{requestId} for the participant
request and payouts/{payoutId} for reserved funds, provider submission, provider status and
accounting references. The backend uses the same deterministic payout intent ID for both.

## Canonical record

A canonical payouts/{payoutId} record contains:

| Field | Meaning |
|---|---|
| id, userId | Stable payout ID and participant owner |
| amountCentavos, currency | Immutable requested amount in integer PHP centavos and PHP |
| requestStatus | Request lifecycle: PENDING_ADMIN_APPROVAL, APPROVING, PROCESSING, PAID, REJECTED, FAILED, REVERSED |
| request | Request snapshot: key, requested time, masked recipient, reviewer and legacy source path |
| status | Existing payout execution/provider lifecycle; Xendit state after approval |
| provider, providerIdempotencyKey, referenceId | Provider and stable Xendit idempotency/reference identifiers |
| providerPayoutId | Xendit payout identifier, when created |
| reserveLedgerEntryId, ledgerEntryId | Accounting references; never regenerated by migration |

Only a masked account number is copied. Full GCash account details remain under the restricted
server-only payoutAccounts/{uid} path.

## Safe rollout order

1. Back up Realtime Database and deploy a runtime version that reads/writes canonical payouts
   request fields while temporarily maintaining payoutRequests as a compatibility projection
   for released Android clients.
2. Run the migration in dry-run mode and review every error. A processing/terminal request
   without its matching provider payout record is rejected for manual reconciliation.
3. Apply only after the runtime cutover is deployed and verified. The script requires both
   --apply and --ack-runtime-cutover before it writes.
4. Verify wallet history, admin review queue, wallet request locks, provider IDs, ledger
   references and payout reconciliation queue against the backup.
5. Keep payoutRequests intact during the compatibility window. Remove its reads/writes and
   RTDB rule only in a separate release after supported Android clients use payouts.

IMPORTANT: this change supplies additive migration tooling and tests. It does not perform a
live migration, deploy Functions, or remove the legacy path. Do not run apply mode until step 1
(runtime cutover) has shipped; the current callable still uses payoutRequests as its request
source.

## Run

From the repository root:

    npm --prefix functions run test:payout-migration
    FIREBASE_DATABASE_URL="https://YOUR_DATABASE_URL" npm --prefix functions run migrate:payouts

The migration command is dry-run by default and uses Application Default Credentials. To write:

    FIREBASE_DATABASE_URL="https://YOUR_DATABASE_URL" npm --prefix functions run migrate:payouts -- --apply --ack-runtime-cutover

Run only from a trusted operator machine with credentials restricted to the intended Firebase
project. The script never deletes payoutRequests records. It uses a transaction for each
destination record and preserves existing provider status, provider payout ID, reservation and
ledger references. It refuses owner/amount conflicts and completed requests without a matching
provider payout record.

## Access control

payouts remains server-write-only. Reads remain limited to the record owner or an administrator,
and the existing userId index supports owner-scoped queries. payoutRequests rules remain during
compatibility. No recipient account number, ciphertext, personal mobile number or address is
copied into payouts.
